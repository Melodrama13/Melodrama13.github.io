# 活动永久标识与预测顺序表

预测只按永久标识 `key` 查找当前活动。开发者维护 `public/data/pjsk_prediction_order.json`，用户保存的预测携带自己的 `key`；不再使用第二份排期登记 JSON。

## 顺序与命名

顺序表包含 `version: 2` 和 `keys`。列表始终从数字活动 0 开始，数组下标就是当前数字活动 ID。当前 259 个位置覆盖 0–258；联动等非数字活动沿用 `c6` 等特殊 ID，不占位置。

历史与未来普通活动都使用 `YYMonN`，例如 `20Nov1`、`26Nov2`。现有标识保持不变：0 为 `20SepRelease`，219 为 `26Oct1`，220 为 `26Oct2`，223 为 `26Nov1`，224 为 `26Nov2`。测试、终章、总集篇使用 `26NovTest`、`25SepFinal`、`Compilation007` 等名称。

名称只在首次创建时确定。调整日期、跨月或改变公开状态都不改名，不根据日期重新推断身份。永久名称不得重复，也不得把已取消的名称分配给另一个活动，避免旧备份恢复到错误活动。

`version` 是文件格式版本，日常插入、取消、公开活动不修改它。顺序表继续使用版本 2，预测文件继续使用版本 5；没有需要维护的 `firstEventId` 或排期修订号。

## 用户预测

```json
{
  "id": 220,
  "predict_schema_version": 5,
  "key": "26Oct2",
  "event_title": "[预测] 箱活",
  "event_type": "箱活",
  "event_attribute": "Pure"
}
```

`key` 决定身份，`id` 仅记录保存时的当前编号。加载、导入和保存时按最新顺序表重新计算 ID，卡片的 `EventID` 和合成 `CardID` 同步更新。新版记录不含 `predict_schedule_index`、`predict_shift_count`、`predict_schedule_key` 或 `scheduleRevision`。

用户预测只保存实际填写的内容，不自动生成每个活动的空预测。测试、终章、总集篇仍不能预测，因此新增这些标识只影响站点顺序及活动资源。

联动使用 `c7`、`c8` 等自身 ID，不写数字活动的 `key`，也不加入顺序表。开发者在官方公布后手动添加活动占位及对应卡片阵容；网站不会预先生成联动。基础活动标题为空且对应卡片阵容非空时，用户只能预测花色和技能。人选、人数、星级、组合、卡片 ID 及 `collab` / `collab_t` 类型均以卡片 JSON 为准，保存和导入时都会恢复固定阵容。类型不按星级推断：`collab` 不计入真限定统计，`collab_t` 按真限定规则统计。

所有 `cN` 使用同一套规则，可保存、刷新、导入导出及生成完整阵容的单源或多源预测图；数字活动增删与重排不会改变联动身份。基础活动标题非空时，与普通活动一样立即锁定并清理预测，无需检查卡片花色或技能是否公开。已公开的 `c6` 不再参与预测。

## 维护排期

- 插入活动：在正确位置插入新名称，保留后面的已有名称。比如在 `26Nov1`、`26Nov2` 之间插入 `26NovTest`，前者仍对应 223，测试对应 224，后者对应 225。用户预测只跟随自己的 `key`。
- 删除或替换未公开活动：从表中移除旧名称，按需要插入新名称。旧预测找不到名称后清理，绝不回退到旧编号。将 `26Nov3` 换成两个总集篇时，原预测失效，后续预测继续跟随原名称。
- 调整日期：更新活动资料，保留名称。
- 正式公开：基础活动 `event_title` 非空后停止应用并清理对应预测；历史顺序位置和名称永久保留。每次活动公开无需更新顺序表。
- 扩展未来月份：在表尾追加名称，并添加对应活动占位资料。

`public/data/pjsk_events.json` 只保存当前数字 ID、日期、类型等资源资料，未公开活动也不保存永久 `key`。永久名称只在开发者顺序表和用户预测中出现；前端先由顺序表取得当前 ID，再读取该 ID 的活动资料。

排期变动时，开发者一起维护活动 JSON 的当前数字 ID、占位资料和顺序表。新增未公开活动需有对应占位资料；已被官方源收录的活动可由同步填入。同步按当前活动 ID 合并官方字段，并保留原有字段保护规则。它不会编辑、追加或重排开发者顺序表，也不会搬移占位编号。

活动同步只读取当前活动资料和官方资源，不读取顺序表，也不需要旧顺序记录或 Git 历史。它沿用原有的按 ID 合并、补齐空字段和保护非空字段规则。已有的测试活动通过本地“测试”类型或官方标题中的 `テストイベント` 识别；总集篇以开发者标注的类型为准，不根据尚未确认的官方类型字段或标题猜测。

同步后运行 `npm run check:prediction-order`，独立检查活动资料与完整顺序表。缺少活动行、数字 ID 重复、名称重复或特殊类型不一致时检查失败；检查不会修改资料。`npm run build` 的 `prebuild` 会自动运行该检查，因此自动同步与其他构建流程都在构建、发布前发现错误。用户预测继续按自己的永久 `key` 自动对应最新位置，联动沿用非数字 ID。

## 旧备份迁移

`src/domain/legacyPredictionMigration.js` 保存一次性冻结的旧编号转换规则。v4 及更早的本地预测和导入备份，先转换成原永久名称，再按最新顺序查找。该模块中的旧名称、数字范围及测试排除规则描述旧格式，不随以后排期更新。

曾使用 `predict_schedule_key` 的记录也可导入，保存及导出统一写成 `key`。两个字段同时存在时必须相同；显式 key 无效或已经消失时，不得回退到 id 或旧顺序字段。新版数字预测缺少 key 会拒绝导入，联动继续直接识别特殊 ID，并拒绝同时携带数字活动 key 的混合身份记录。

迁移后的本地数据及新导出只使用新版标识。已经下载到设备的旧文件不会被网站改写，重新导出即可得到新版格式。

## 加载与发布

只有活动资料与完整顺序表成功加载并校验后，才清理本地预测。网络失败、表缺失、部分资料、名称冲突、重复 ID 或特殊类型不一致均保留原预测。无效旧资源缓存会被跳过，再尝试网络获取最新资料；有效当前缓存仍可直接使用。

顺序表、活动资源和代码应一起发布，公共缓存及资源版本包含顺序表。活动同步不再需要 `--prediction-order-file`，也不读取、写入或生成 `pjsk_prediction_schedule.json`，不向活动资料补写永久 key。检查活动副本时可运行 `npm run check:prediction-order -- --events-file 路径 --order-file 路径`。

CI 从私有脚本仓库的 `scripts/` 安装 `.mjs` 文件到本站被忽略的 `sync-scripts/`，活动同步入口是 `sync-events-other-source.mjs`。本地同步也使用该目录，公开的 `scripts/` 只保存构建和检查工具。活动脚本目前采用私有仓库现有版本；后续修改同步脚本时需同时更新私有仓库。本次本地实施不代表已经提交或发布网站。

## 验证范围

本地验证记录保存在 `.codex/prediction-schedule/key-only-*`，不作为网站资源发布。覆盖大批插入、取消与两部分替换、公开清理、联动隔离、卡片重定位、旧备份、编辑保存、导入导出、真实同步命令，以及错误资源和旧缓存下的预测保护；浏览器覆盖 Chromium 与 WebKit。

移除基础活动 key 后的验证保存在 `.codex/prediction-schedule/no-event-key/`，另外覆盖无 key 资源、旧顺序恢复、连续插入、同步幂等、干跑无写入、Git 新检出、字段保护及恢复失败时不改数据。

通用固定阵容联动的验证保存在 `.codex/prediction-schedule/fixed-collaboration/`。覆盖任意 `cN`、3/9/26 名不同人物的源卡片、混合星级与类型、篡改导入纠正、基础标题锁定、数字活动插入隔离、统计不重复及多源分支。按当前游戏规则，同一期活动每个人只有一张卡。Chromium 和 WebKit 均验证了编辑保存、刷新、JSON 导入导出和完整阵容 PNG 导出；临时活动与卡片只注入测试浏览器，不写正式 JSON。自动 WebKit 验证不代替实机 Safari 验收。

独立同步与顺序检查的验证保存在 `.codex/prediction-schedule/independent-sync-checks/`。覆盖不依赖顺序表的同步、按当前 ID 公布活动、新增官方行、重复同步、字段保护、已有测试活动的标题识别、人工总集篇占位及联动隔离。独立检查覆盖无效或缺失顺序表、缺少活动行、重复 ID、重复标识和特殊类型冲突；预测与资源加载回归继续验证永久 key 对位和异常资源下的预测保护。正式 JSON 保持不变。
